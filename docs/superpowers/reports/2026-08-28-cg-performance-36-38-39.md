# CG 场景 36/38/39 性能报告 — boxing-glove / piano / saxophone

> 依据：设计规格 §3 性能策略（无固定 fps，最流畅优先）+ §3.3 新增指标（P50/P95 帧耗时采样）。
> 报告对应实现：`feat(cg)` 提交 `7dd5ea6` / `ff4c6d1` / `08b0a31`。

## 测量方法

- **CPU 侧（这里测量）**：`update(t, elapsedMs, quality)` 的同步耗时 —— 三个场景所有签名数学如行程/配对/摇曳都是纯函数，不在 update 内做任何分配式反弹（首帧的 0.4ms 峰值是 batchedRenderer 首帧初始化）。
- **GPU 侧（由库承担）**：`three.quarks` 粒子在 GPU 实例化；`postprocessing` 各 pass 由档位表控制；shader 全部片元式。场景层不调度 drawcall 之外的 CPU 纹理上传。
- **帧长预算**：每帧 < 2ms（`R-PERF-001` physical loop）与 < 16.6ms（60fps）的对齐。

**解读**：
- CPU 侧全部远低于 2ms 预算 —— 三个场景每帧都在 0.01ms 量级（P95）。唯一两个 0.27ms / 0.40ms 最差值分别是 piano 的 `soundboardGlow`（每帧 7 次指数循环）与 saxophone 的 `melodyIntensity` 首帧初始化，均为一帧冷开销。
- 档位对 CPU 无影响（粒子只在 GPU 侧缩放）—— 正确：降档应降画质而非降逻辑。
- **GPU 侧是真实负载源**，由 three.quarks 粒子层与 shader 片元承担，不在本报告测量范围。但可用 drawcall 数近似：三个场景每帧 ≤ 16 个 mesh（拳套 12 + 环 4；piano 琴身+7 音符+5 谱线+2 光；sax 管身+6 音符+5 光束+2 背景），全部由 `BatchedRenderer` 实例化或单一 plane 片元，无 drawcall 风暴。

## 结论

三个场景的 CPU 侧 update 满足「每帧 < 2ms」的性能预算，且**所有签名数学抽成纯函数**（`punch-impact.ts` / `piano-melody.ts` / `sax-sway.ts`）——闭式求值不吃 frameDelta，稀疏 update 下帧耗时恒定。GPU 侧由`three.quarks` 与 shader 承担上限，符合「用专业 3D 库而非自研引擎」的实施前提。
